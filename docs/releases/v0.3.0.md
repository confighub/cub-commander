# v0.3.0 - Read-Only Resource Evidence

Previous release: v0.2.1. This additive release introduces Resource detail
`3 Evidence` using Scout's bounded JSON provider. It requires Scout v2.10.0;
publish/install Scout first. Publication and final verification are recorded in
[observer #525](https://github.com/confighub/cub-scout/issues/525).

## Install Or Upgrade

```sh
# Fresh installs:
cub plugin install confighub/cub-scout@v2.10.0
cub plugin install confighub/cub-commander@v0.3.0
# Existing installs:
cub plugin upgrade scout@v2.10.0
cub plugin upgrade commander@v0.3.0
cub scout version
cub commander version
cub commander --scout-binding '<target-id>=<kube-context>'
```

Alternatively, supply `--scout-binary /absolute/path/to/cub-scout` to use a
standalone provider without changing installed plugins. Scout v2.9.0 and other
incompatible providers produce unavailable evidence, not broader fallback reads.

## Behavior

- Select one Resource, then `3 Evidence`. Target ID to kube-context binding is
  explicit. The selected Resource must supply its own exact identity; joined
  rows, names, labels and current kubectl context do not fill gaps.
- One captured snapshot retains timestamps and a stale indicator visible even
  while scrolling. Tab revisits make no provider calls; `r` discards the old
  snapshot and starts a new read. Failed refresh never restores old success.
- Display the exact scope, shell-safe invocation and bounded evidence/omissions.
  Cancellation, timeout, output bounds and process reaping limit background work;
  late results cannot overwrite another selection.
- This tab is read-only. Existing Data editing and confirmation-gated rollout
  actions remain separate. Standalone Scout exploration is not replaced.

This is neither desired/live comparison nor proof of delivery or application
success. Retained snapshots do not revalidate credentials. There is no new fleet
cache, automatic polling, implicit source join or mutation surface.

## Proof And Limits

Full offline tests, focused repeats, race checks, build/vet, exact scope and
request-count tests, narrow-terminal rendering and a terminal smoke cover the
implementation. The opt-in integration test uses a synthetic intended-state API
and a real existing non-production Kubernetes object. It verifies one intended
state GET, two provider calls (open/refresh), and none on tab revisits.

Authenticated ConfigHub-to-cluster mapping proof remains unavailable until user
login and explicit test Target/context scope are supplied. This limitation is
not disguised as a passing live test. The release assets cover macOS/Linux,
amd64/arm64, with per-binary SHA-256 files. Final downloaded-artifact and actual
plugin-host checks are recorded in #525 after publication.
